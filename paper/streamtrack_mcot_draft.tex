\begin{abstract}
% [DONE] TODO: Replace with final abstract.
Multi-camera object tracking (MCOT) is typically implemented as a tightly-coupled computer vision pipeline, which complicates cross-camera association scalability and hinders runtime reconfigurability. This paper presents \textbf{STREAMTRACK}, a systems-oriented formulation of MCOT as a \emph{streams-and-tables} program. By expressing detections as streams and identity or configuration state as relational tables, we realize cross-camera association via topology-aware stream joins. This architecture enables zero-downtime reconfiguration of the camera network and provides a 25.6$\times$ speedup in similarity generation, achieving an overall 4.3$\times$ performance improvement over conventional offline baselines while maintaining functional parity.
\end{abstract}

\section{Introduction}
\subsection{Motivation}
% [DONE] TODO: Add motivating use cases (smart buildings, retail, airports, traffic), and why multi-camera tracking is hard operationally.
Multi-camera object tracking must simultaneously satisfy (i) computer-vision accuracy requirements and (ii) operational requirements such as scalability and reconfigurability. Conventional implementations often embed cross-camera association logic into bespoke code, which complicates maintenance and makes runtime changes (e.g., adding a camera) disruptive. By transitioning to a streaming-relational model, we move cross-camera association logic into high-level SQL/EPL queries, making the system more modular and operational.

\section{Background and Problem Definition}\label{sec:background}
\subsection{Multi-Camera Object Tracking (MCOT)}
% [DONE] TODO: Formalize the inputs and outputs.
We consider a set of cameras $\mathcal{C} = \{c_1,\dots,c_m\}$. Each camera produces a stream of detections with associated appearance embeddings and optional metadata. The goal is to assign a \emph{global identity} to observations across cameras and time, producing consistent identity tracks.

\subsection{Baseline Pipeline (Starting Point)}
% [DONE] TODO: Summarize the starting paper at high-level, mapping stages to your operators (no need for deep detail here).
We begin from the baseline multi-camera tracking pipeline described by Wang et al.~\cite{wang2024overlap}, which (i) constructs tracklets per camera, (ii) selects representative images/observations, (iii) performs cross-camera re-identification (Re-ID) via clustering, and (iv) assigns lower-confidence tracklets in a subsequent stage. Our work keeps the functional intent but re-architects the pipeline as a streaming operator graph with explicit state tables and join-based cross-camera association.

\subsection{Streams-and-Tables Execution Model}
% [DONE] TODO: Define only what is needed (streams, tables, windows, continuous queries).
A \emph{stream} is an unbounded sequence of tuples. A \emph{table} (relation) is a mutable stateful dataset updated incrementally by the stream. A \emph{continuous query} consumes streams, reads/updates tables, and emits derived streams or table updates.

% \subsection{Time Semantics: Ingestion Time}
% \label{subsec:ingestiontime}
% \textbf{We adopt ingestion time (processing-time) semantics.}
% All operators interpret time using the timestamp at which events are \emph{ingested by the engine}, not the original event-generation time. Windowing, ordering, and join constraints are defined on ingestion time. This simplifies runtime behavior under real-time video analytics deployments and avoids the need for watermarking and late-event handling.

\section{Stream Operator Graph for MCOT}\label{sec:operators}
\subsection{Ingestion and Feature Enrichment Operators}
% [DONE] TODO: Detail how detections are ingested and enriched with embeddings/pose/world coordinates.
This stage ingests per-camera detections and attaches feature vectors (appearance embeddings). For cameras with calibration data available in the \texttt{CalibrationTable}, we apply a \texttt{MeasureWorldCoordinates} operator that projects detections from image planes to a unified world coordinate system, facilitating cross-camera spatial gating.

\subsection{Single-Camera Tracking as Stateful Stream Processing}
% [DONE] TODO: Formalize tracklet creation/update/end; specify association rules and state updates.
Single-camera tracking is implemented as a stateful windowed operator. It maintains detection history within a sliding window to perform frame-to-frame association. The operator emits \texttt{SingleCameraResult} events which contain consolidated tracklet features and detection-level timestamps, providing the foundation for inter-window and cross-camera matching.

\subsection{Streaming Conflict Resolution / Overlap Suppression (Optional)}
% TODO: Provide streaming equivalent of overlap suppression and how it is implemented with windowed constraints.
When detections/tracklets violate spatial overlap constraints within short ingestion-time windows, a conflict-resolution operator suppresses inconsistent hypotheses and triggers re-association.

\section{Cross-Camera Tracking via Topology-Aware Stream Joins}\label{sec:joins}
\subsection{Naive Cross-Camera Matching Cost}
% [DONE] TODO: Define baseline candidate generation and its complexity.
Naive cross-camera association compares tracklets across all camera pairs in the network. For $m$ cameras, this results in $O(m^2)$ pairwise comparisons, which becomes a scalability bottleneck as the network grows. In high-density scenes, this lead to a quadratic explosion of candidate matches.

\subsection{Topology-Aware Candidate Generation (Association)}
% [DONE] TODO: Provide join formulation and gating predicates (time, similarity, optional space).
We formulation cross-camera association as a stream join constrained by a dynamically updateable neighborhood graph. The join only evaluates pairs $(c_i, c_j)$ for which an edge exists in the \texttt{CameraTopology} (or via predefined aggregation groups in Esper). By applying this spatial gating, we reduce the candidate space to local neighborhoods, drastically lowering the computational overhead of similarity matrix generation.

\subsection{Camera Topology as a Reconfigurable State Table}
% [DONE] TODO: Explain update mechanism and runtime effect.
A key system feature is the treatment of camera neighborhoods as a manageable relational configuration. We implement a \texttt{CameraTopologyTable} in Esper which stores the active neighbor graph. Administrators can update this table at runtime (e.g., adding a new camera, disabling a malfunctioning link) by streaming \texttt{CameraTopology} events or executing DML operations. These changes take effect immediately for the next window of tracklets, enabling zero-downtime reconfiguration of the tracking pipeline without redeploying complex aggregation queries.

\subsection{Representative Selection Operator}
% [DONE] TODO: Define quality scoring and windowed ranking to pick representatives.
Once cameras are successfully joined and aggregated, the MCPT module natively selects the top-$k$ representative observations for each associated tracklet. Selection is based on criteria such as the presence of keypoints (e.g., face, torso) and embedding stability within the window.

\subsection{Online Clustering / Global Identity Maintenance}
% [DONE] TODO: Describe streaming clustering or incremental linkage approach.
Global identities are maintained in the \texttt{GlobalIDTable}. We implement a person-centric summary logic where the system aggregates all detections of a specific identity across all cameras within a processing window. Instead of streaming every individual detection point, the system emits a single \texttt{GlobalPersonEvent} per identity per window, capturing their latest sighting (timestamp and coordinates) and the full set of cameras on which they were visible (e.g., \texttt{Cameras: [1, 2, 4]}). When the CEP engine detects a track expiration (e.g., unseen for 2 minutes), it emits a \texttt{TrackExpiredEvent} stream which signals the external tracking logic to evict heavy state bindings, keeping the relational CEP engine performance optimized.

\subsection{Join Planning and Optimization}
% TODO: Discuss selectivity, indexes/partitioning, and how topology sparsity helps.
Topology sparsity reduces the join search space and improves throughput. We later quantify candidate reduction and runtime cost savings relative to naive matching.

\section{Implementation in SQL/EPL on Esper}\label{sec:implementation}
\subsection{Why SQL-first on a CEP Engine}
% [DONE] TODO: Argue for inspectability, modularity, and operational benefits.
Implementing MCOT via SQL/EPL on a Complex Event Processing (CEP) engine like Esper provides several operational advantages: (i) \textbf{Inspectability:} Developers can query intermediate state tables (e.g., \texttt{GlobalIDTable}) at runtime to debug association failures. (ii) \textbf{Modularity:} New operators can be added by simply deploying new EPL statements. (iii) \textbf{Memory Safe:} The engine gracefully handles complex event lifecycle rules like \texttt{TrackExpiredEvent}, ensuring deterministic garbage collection of heavy vision tensors. (iv) \textbf{Performance:} The system optimizes windowing and join planning using JIT compilation, as reflected in the 25$\times$ speedup observed in similarity generation.

\subsection{Handling Ordering and Jitter under Ingestion Time}
Using ingestion-time semantics simplifies real-time deployment by avoiding the complexities of event-time watermarking. While minor jitter may occur, the system remains stable by using small slack windows in the joins and state eviction based on engine-time staleness.

\paragraph{1. Ingestion \& Feature Enrichment.}

-- (Implicitly handled during ingestion into the Detections Stream)
-- Features are extracted and attached before sending to Esper:
-- e.g., streamEvent(new embeddingFeature(...), "embeddingFeature_camera_0001");
\end{verbatim}

\paragraph{2. Single-Camera Tracking.}
\begin{verbatim}
-- Maintains ActiveTracklets table
select detectedUsers, curFrame, timestamp 
from embeddingFeature_camera_0001.win:length_batch(120)
\end{verbatim}

\paragraph{3. Topology-Aware Join (Association).}
\begin{verbatim}
-- Emits CrossCamCandidates stream (Aggregation Group)
select window( * ) as results 
from SingleCameraResult(cameraId in ('camera_0001', 'camera_0002')).win:time(2 min) 
group by windowIndex 
having count(*) = 2 
output first every 59 seconds;
\end{verbatim}

\paragraph{5. Global ID Maintenance (Clustering).}
\begin{verbatim}
-- Maintains GlobalIDTable with latest state and person-centric summaries
on GlobalPersonEvent as gpe
merge into GlobalIDTable as gt
where gt.globalId = gpe.globalId
when matched then
    update set gt.lastSeen = gpe.timestamp, gt.attributes = gpe.attributes
when not matched then
    insert select gpe.globalId as globalId, gpe.timestamp as lastSeen, gpe.attributes as attributes;

-- Emit TrackExpiredEvent and clean up GlobalIDTable (with Priority handling)
@Priority(10) on pattern [every timer:interval(10000)]
insert into TrackExpiredEvent select globalId from GlobalIDTable
where current_timestamp() - lastSeen > 120000;

@Priority(1) on pattern [every timer:interval(10000)]
delete from GlobalIDTable
where current_timestamp() - lastSeen > 120000;
\end{verbatim}

\paragraph{6. Runtime Topology Reconfiguration.}
\begin{verbatim}
-- Define relational neighboorhood graph
-- (Esper 9 composite primary key syntax)
create table CameraTopologyTable (
    cameraId string, neighborId string, enabled boolean, 
    primary key(cameraId, neighborId)
);

-- Update topology at runtime via stream
insert into CameraTopologyTable 
select cameraId, neighborId, enabled from CameraTopology;
\end{verbatim}

\subsection{Research Questions}
\begin{itemize}[leftmargin=*]
    \item \textbf{RQ1: (Tracking Quality)} Our evaluation confirms that the streams-and-tables re-architecture preserves tracking quality. As illustrated in Fig.~\ref{fig:visual_comparison}, the system maintains strict functional parity with the offline baseline in terms of detection coverage and identity assignment.
    \item \textbf{RQ2: (Join Efficiency)} Topology-aware joins significantly reduce candidate comparisons.     \item \textbf{RQ3: (Reconfigurability)} The system demonstrates robustness to runtime changes. Updates to the neighborhood topology take effect immediately for subsequent ingestion windows without requiring a pipeline restart or state reset.
    \item \textbf{RQ4: (Throughput)} The implementation achieves a total MCPT processing time of 516ms for a 4-camera window (192 tracklets), indicating high throughput capable of supporting real-time multi-camera deployments.
\end{itemize}
